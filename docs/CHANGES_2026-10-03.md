# Изменения 2026-10-03 (локально, не опубликовано)

Замеры — RADV, ограничение `taskset` до 4 ядер / 8 потоков, настройки портативной конфигурации
(вывод 1280×720, FSR 3 Performance, сцена 640×360), без лимита FPS. Стенд:
`out/bb-probe` из исходников, сохранение `docs/savedata_route`, скриптовый вход в уровень.

## Смена разрешения на лету — по умолчанию выключена

`live_resolution` без значения (новая установка, лаунчер, меню) теперь означает «выключена»:
для вывода не 1080p — патч разрешения при старте, как в 0.1. `auto` (проверка видеокарты) и `1`
выбираются явно. Тесты `test_run_settings`.

## AppImage без моделей FSR 4.1.1

Модели извлекаются из DLL AMD и в публичный пакет не входят (как в 0.1): `packaging/default.nix`
кладёт `fsr4_411` только с `BB_PACKAGE_FSR411=1`; иначе их ищут в каталоге данных.

## Портативные системы: запуск и сборщик текстур

- **AppImage не запускала игру на NixOS** (код 127 без сообщения): `run.sh` читал
  `live_resolution` через `sed`, которого нет в окружении AppImage. Теперь только встроенные
  команды bash; тест `test_live_resolution_without_sed_or_grep`.
- **Сборщик текстур на встроенных GPU** (`TextureCache::GarbageCollectImages`). Бюджет считался
  как «все кучи минус 8 ГБ для системы» (на портативной системе ~1 ГБ), а занятость — по кучам GTT, где лежат и
  буферы с памятью игры (~4 ГБ). Сборщик постоянно работал в «агрессивном» режиме: на каждой
  отправке команд (~66 за кадр) выкидывал до 40 текстур, не использованных 2–3 кадра, и снова
  их загружал, а изменённые GPU асинхронно записывал обратно в память игры. Теперь на встроенных
  GPU пороги — доля текущего бюджета драйвера (`VK_EXT_memory_budget`): сбор с 70%, нехватка с
  85%, критично с 95%. В журнале при нехватке: `Texture cache: memory pressure, …`.
  `BB_GC_BUDGET_MB=N` — то же правило с заданным бюджетом на любом GPU (проверка на ПК).
- **Запись вытесненной текстуры обратно в память игры теперь синхронная**, пока страницы ещё
  защищены. Отложенная запись приходила после снятия защиты — поверх того, что игра успела туда
  записать (например, кучу после выгрузки локации). Возможная причина `Guest fault 0x263b8e7` на
  Деке при подгрузке карт; **на ПК этот вылет тоже был один раз за ~10 прогонов, его причина не
  найдена** (порог нехватки памяти на ПК ~11 ГБ, сборщик туда не попадает).

## Живая смена разрешения дешевле

Раньше уменьшались только цели 1920×1080; постобработка игры в полуразрешении (960×540, в том
числе цепочка bloom с mip-уровнями) шла в полном размере и каждый кадр пересэмплировала цвет
сцены. На портативной системе один такой проход стоил ~8.4 мс (против ~1.4 мс при патче разрешения).

- Цели 960×540 уменьшаются тем же коэффициентом, что сцена (ProxySize). Пересчёт FragCoord в
  шейдерах не меняется: 960/320 = 1920/640.
- Mip-цепочки полуразрешения: отдельная уменьшенная копия на каждый уровень (ключ — изображение и
  уровень); выборка одного уровня читает копию, выборка всей цепочки — родное изображение после
  пересэмплирования.
- Переключатель `BB_TOGGLE_FILE` бит 50 (`SceneHalfRes`) — прежнее поведение.
- `BB_SCENE_DEBUG`: ещё печатает пересэмплирования (`Scene resolve/fill`) и чтения уменьшенных
  целей в полном размере с причиной (`Scene native read`).
- Тест: `scene-resolution-test` — копия mip-уровня 2 цепочки 960×540 и её возврат в родной уровень.

Результат на ПК (4c/8t): занятость GPU живого пути 3.41 → 3.23 мс на кадр, проход `5a619b89` —
320×180 вместо 960×540. Картинка совпадает с режимом патча (bloom и туман считаются в
пониженном разрешении, как при патче). Осталось: ~9 пересэмплирований и ~7 обратных заливок
цвета сцены 1080p за кадр (копирования, `9a9cf8a9`, композиция UI).

**Почему живой путь всё равно дороже на CPU:** игра считает экран 1080p и рисует в проходе
освещения (`vs 8747a367`) 335 источников света вместо 42 при патче (мелкие источники
отбрасываются по размеру на экране): 975 draw-вызовов на кадр против 679. Это решение самой игры.

## TAA: мерцание тонких объектов вдали

Прутья окон, перила и края обломков мерцали: в фазе jitter, где тонкий объект не попадает в
центр пикселя, проверка глубины отбрасывала историю (в ней объект ближе текущего фона). Теперь
при движении меньше пикселя такая история остаётся и ограничивается цветом соседей (как в TAA без
отбрасывания по глубине). Переключатель бит 55 — прежнее правило.

Метрика: 30 кадров подряд при неподвижной камере (`BB_PRESENT_DUMP_COUNT=30`), средняя вторая
разность яркости по времени (мерцание кадр-к-кадру, плавная анимация почти не влияет), ×1e-3:

| | среднее | p99.9 |
|---|---|---|
| было (2 прогона) | 0.367 / 0.381 | 23.2 / 22.0 |
| стало (2 прогона) | 0.266 / 0.293 | 12.2 / 13.1 |
| без TAA и jitter | 0.428 | 16.8 |

Мягкое ограничение по цвету для неподвижных пикселей и обрезка по дисперсии мерцание не
уменьшили (дисперсия — увеличила). Тесты `taa-shader-test`: добавлены «thin line missed by this
frame keeps history», «static disocclusion is clipped», «moving disocclusion is rejected».

## Апскейлеры: сверка с аудитом от 2026-10-02

Аудит смотрел версию с GitHub (`cc001f9`); по локальному коду:

- Native AA вне 1080p (2.1) — уже исправлено (`w > ow`).
- FSR 4 v07 и HDR-флаг (2.2): провайдер сохраняет флаги контекста, но не читает их — флаг на
  результат не влияет. На пути с патчем вход действительно LDR (после тонмаппинга) — ограничение
  самого пути.
- Небо (4.1) и порог глубины объектных векторов (4.4) — уже исправлены (поворот без переноса,
  относительный порог, полная точность глубины).
- **Mip bias (4.7) — сделано:** в проходах G-buffer (5+ целей) при уменьшенной сцене смещение
  LOD сэмплеров log2(рендер / вывод) (на портативной системе −1); тени, постобработка и UI без изменений. В
  журнале `Upscaler: scene texture LOD bias -1.00`. Переключатель бит 57.
- Не сделано: классификация частиц для jitter (4.2), сброс истории на смену камеры (4.8).

## CPU на слабых процессорах: замер

Режим патча, 4c/8t, 209 FPS. Потоки (% одного ядра, пользователь + ядро): `bb:DrawRec` 72 + 14,
поток команд GPU 56 + 20, `bb:VkRecorder` 72 + 1 (в основном время RADV), основной поток игры
46 + 10, четыре потока подготовки draw по ~20. Всего занято ~545% из 800%: предел —
последовательная цепочка «поток команд → запись draw → запись Vulkan». Дальнейший рост требует
распараллелить запись Vulkan (несколько командных буферов) — крупная переделка, не начата.
