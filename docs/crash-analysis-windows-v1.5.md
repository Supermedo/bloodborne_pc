# Разбор четырёх падений Windows v1.5

Проверен именно `Supermedo/bloodborne_pc`, тег `windows-v1.5`, коммит
`9514b1923571ea6fa76b34b3bca49b7146f43b41`. Исполняемый файл извлечён из опубликованного
`Bloodborne-Windows.zip`; его SHA-256:
`8e83d0d3ca3e0bc78cb061623cb59ae68849437e90497f2a1123553d23a319a8`.
Адреса ниже расшифрованы по таблице символов и дизассемблированию этого файла,
а не по адресам новой сборки. В архиве отсутствуют отладочные строки исходников.

Готовая локальная сборка: `out/Bloodborne-Windows-crash-fix.zip` (около 103 МиБ).
Распакуйте в отдельную папку; для продолжения своего прохождения перенесите туда
`user` и `bbport.ini` из старой установки, а при необходимости — `mods`, `mods.json`,
`patches.json`. Запустите новый `Bloodborne.exe`. Подготовленные файлы `out` переносить
не требуется: новый launcher подготовит их заново. Папка игры выбирается в launcher.

Архив включает runtime, launcher со встроенным Python/Tk, зависимости Windows,
DLSS и прежние FSR4 assets. После распаковки проверены Vulkan, полный запуск GPU,
создание дампа, запуск preparation script и встроенный Tcl/Tk с PATH без MSYS2.

## Гонка очереди команд

В v1.5 `Liverpool::ProcessCommands()` сначала проверял `num_commands` для ожидания
`DrainDrawPipe()`, затем отдельно проверял его в `while`. Между проверками другой поток
мог поставить запрос чтения GPU-памяти. Первая проверка видела пустую очередь и пропускала
ожидание, вторая уже запускала callback. Поток декодирования и поток отрисовки одновременно
меняли кэши, барьеры и текущий блок Scheduler.

`KickRecording()` перемещает `record_chunk` в рабочую очередь и лишь затем получает новый.
Другой поток в этот момент читал `used` по `nullptr + 0x20000` или записывал `next`
по `nullptr + 8`. Это соответствует инструкциям и регистрам во всех трёх падениях bb-probe.
Гонка также допускает повреждение записанных Vulkan-команд, но без стека первого падения
нельзя утверждать, что именно она вызвала исключение NVIDIA.

Исправление ожидания перед каждой командой уже включено в перенесённый upstream 0.3/0.4
(локальный merge `b1d2bfa`). При разборе логов этот путь выделен в production-функцию
`DispatchHostCommands`, используемую Liverpool и регрессионными тестами. После наблюдения
пустой очереди функция возвращается; поздняя команда исполняется при следующем вызове,
после передачи владения от потока отрисовки. Callback запускается без mutex очереди.

## Проверки

- Детерминированный тест: команда поступает сразу после наблюдения пустой очереди, пока
  настоящий DrawPipe worker заблокирован. Callback может выполниться только после Drain.
- Дополнительно проверены повторное добавление команды из callback и ожидание перед
  каждым callback.
- Контрольная сборка теста с алгоритмом v1.5 воспроизводимо завершается на проверке
  `!draw.active.load()`. Исправленный алгоритм проходит тот же сценарий.
- Vulkan-проверка: 256 пакетов, более миллиона записанных команд, переходы между
  блоками 128 КиБ, три Vulkan recording worker, сегменты 1 КиБ, ordered host copies,
  промежуточные Finish и проверка всех 256 результатов GPU в CPU-памяти. Пройдены оба режима
  `BB_ASYNC_SUBMIT=1` и `0`.
- Полная проверка Windows: 17/17 CTest и 110 Python-тестов (93 успешных, 17 платформенных
  пропусков). Полный журнал локально: `out/crash-validation.log`.

Предупреждения об отсутствующих AMD extensions на NVIDIA, отсутствующий необязательный
profile.bin и сообщения о файлах отдельных карт сами по себе не указывают на причину
этих исключений. Настройки FSR3/FSR4 и object motion в логах различались; нулевой блок
записи команд обнаружен независимо от выбранного апскейлера.

## Диагностика следующего сбоя драйвера

В startup-лог добавлены PE timestamp и SizeOfImage для сопоставления с конкретным бинарным
файлом. При фатальном исключении создаётся Windows minidump с исходным контекстом исключения,
потоками и списком модулей. Системный DbgHelp загружается до запуска игры; дамп пишет отдельный
поток, ожидание ограничено десятью секундами. Ошибка записи не меняет исходный код завершения 3.

По умолчанию дампы находятся в `logs/crashes` выбранной папки данных. `BB_CRASH_DIR`
задаёт другую папку, `BB_CRASH_DUMP=0` отключает их. Никакой автоматической отправки нет.
Отдельный тест реально вызывает access violation в синтетическом гостевом коде и проверяет
код исключения, исходный адрес, потоки, модули и путь с кириллицей в созданном .dmp.

Игровой дамп и сохранение из S:\Games\Bloodborne на этом компьютере недоступны.
Продолжительная игра в проблемных локациях не проверена. Для подтверждения устранения
падения внутри nvoglv64.dll нужен повторный игровой прогон; при повторении — новый .dmp
и журнал с этой сборки.
