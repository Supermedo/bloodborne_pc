# Bloodborne на ПК: фактическое состояние порта и апскейлера

Срез на **29 сентября 2026 года**. Источник — файлы в `game_files`, история Git
`native_probe` до `ac9fe90`, текущие незакоммиченные изменения, сохранённые логи
запусков и локальные тесты. В документе «есть в коде», «запускалось» и «проверено
по изображению» не считаются одним и тем же.

## Краткий итог

Это работающий экспериментальный **нативный Linux-порт**, а не запуск через
полный эмулятор: исходный x86-64 `CUSA03173/eboot.bin` исполняется на CPU ПК,
системные вызовы PS4 обрабатывает собственный HLE-рантайм, графику выводит
Vulkan-ядро на основе shadPS4. Игра доходит до сцены с персонажем, принимает
ввод, работает со звуком и сохранениями; это подтверждают логи запуска,
снимки и видео в корне `native_probe`. Прохождение всей игры, все локации и
отсутствие сбоев этими материалами **не подтверждены**.

**FSR 3.1 temporal upscaling реально работает по проверенному пути с разрешением
сцены, заданным при старте**: лог `логи.md` показывает `960×540 → 1920×1080`,
компоновку UI в 1920×1080 и запуск в тестовом окружении. Текущий путь смены пресета
без перезапуска остаётся проблемным на этой видеокарте: последний
`last_run.log` показывает переключение запрошенных размеров сцены, но FSR-контекст
`1920×1080 → 1920×1080`. По коду уменьшенные цели здесь не выбираются, когда
`D32S8` не поддерживает blit. Следовательно, лог переключения пресетов **не
доказывает реальное снижение разрешения 3D и выигрыш FPS**.

## Что реализовано

### Запуск и производительность

- Гостевой `eboot` и часть оригинальных PRX запускаются вместе с реализациями
  памяти, потоков, файлов, времени, контроллера, аудио, сохранений и сервисов.
  Сеть работает в офлайн-режиме; PSN не реализован.
- SDL3 обслуживает геймпад и запасное управление с клавиатуры. Звук выводится
  через host-аудиосистему; в коде есть исправление темпа `AudioOut` и флаг
  сохранения для отсутствовавших звуков.
- Vulkan-рендерер получил отдельный поток записи команд, подготовку draw на
  четырёх потоках, кеши текстур и буферов, копирование гостевой памяти и пул
  staging-буферов. `docs/parallel_gpu.md` и `docs/ROADMAP.md` содержат
  замеры в отдельных сценах; их нельзя переносить на все конфигурации.
- `BB_FPS=uncap` по умолчанию применяет патч с шагом симуляции по времени
  кадра; доступны `30`, `60`, `90`. Частота вывода ограничивается монитором
  и максимумом 120 FPS. Для диагностики есть `BB_FRAME_STATS=1`,
  `BB_TOGGLE_FILE` и захват структуры кадра через `BB_CAPTURE_TRIGGER`.

### Апскейлер

- В игре нет готового буфера скорости. Порт вычисляет векторы камеры из
  глубины и матриц двух кадров; для геометрии сцены делает субпиксельный
  jitter Halton. Перепроекция статичной геометрии проверялась ранее
  (`docs/upscaler.md`).
- Интегрирован FSR 3.1 через `gpu/third_party/fsr-vulkan`. Native AA работает
  1:1 на HDR-цвете сцены перед постобработкой. Проверенный режим с пониженным
  разрешением использует патч гостевого разрешения, FSR после тонмаппинга и
  отдельную компоновку интерфейса в 1920×1080. Патч UI в текущем дереве
  оставляет его координаты нативными. Явный `BB_RENDER_RES=ШxВ` включает
  этот путь; например, лог `логи.md` подтверждает `960x540`.
- Пресеты в коде: Native AA `1920×1080`, Quality `1280×720`, Balanced
  `1130×636`, Performance `960×540`, Ultra Performance `640×360` для вывода
  1920×1080. Меню ImGui открывается `Insert` или `L3+R3`. В `bbport.ini`
  сохраняются FSR, пресет, резкость, jitter, маска реактивности, режим
  отладки, векторы объектов и счётчик FPS. Текущий конфиг содержит
  `upscaler=fsr3`, `preset=4`, `jitter=1`, `reactive=1`,
  `object_motion=1`, `debug_view=0`.
- Маска реактивности формируется сравнением цвета до и после прозрачных
  проходов. Она опциональна: прежние наблюдения отмечают дрожание тонкой
  дымки при её включении. Настройка по умолчанию в коде выключена, но
  в текущем `bbport.ini` включена.
- В рабочем дереве есть экспериментальные векторы анимированных объектов:
  прошлые позиции вершин, дополнительная цель G-buffer, сопоставление
  отрисовок между кадрами и ограничение на подходящие буферы позы/костей.
  Изменение `object_motion` требует перезапуска. По
  `out/dev/motion-selective.log` история в выбранных draws часто находится,
  без пропусков по ёмкости в показанных интервалах. Это метрика draw, **не
  оценка покрытия пикселей или визуального качества**.

## Текущий дефект динамических пресетов

В `vk_scene_resolution.cpp` функция `SceneTargets::Eligible` требует
`BlitSrc|BlitDst` у формата каждого кандидата. В `vk_rasterizer.cpp`
уменьшенный проход отключается, если неподходящая глубина; от неё же зависит
выбор уменьшенного входа FSR в `vk_temporal_upscaler.cpp`. Сохранённый лог
для тестового адаптера сообщает об отсутствии `blit` у `D32S8`. Позднее добавлен
fallback, который **очищает глубину UI** вместо её копирования, но он не
устраняет требование `blit` у глубины **3D-сцены**.

Итог на этой машине: в `last_run.log` 28 сентября перечислены переключения
`640×360`, `1280×720`, `960×540` и других пресетов, однако созданный
FSR-контекст остался `1920×1080 → 1920×1080 (HDR scene color)`. Сообщение
`Scene resolution: raster ...` отражает запрошенный размер proxy-целей;
оно не измеряет фактически использованный размер каждого draw. Заявления
`README_FIXES.md` и подсказки меню о работающем на всех GPU динамическом
масштабировании сильнее, чем позволяют код и последний лог. `логи.md`
относится к более раннему запуску с автоматическим выбором стартового патча,
который затем изменили в `run.sh`.

## Как воспроизвести подтверждённый путь

Из `game_files` на этой конфигурации:

```bash
BB_RENDER_RES=960x540 BB_FRAME_STATS=1 bash native_probe/run.sh
```

`BB_RENDER_RES` выбирает патч стартового разрешения сцены, а текущий
`patches.py` сохраняет UI в 1920×1080. Смена разрешения таким способом
требует нового запуска. Без `BB_RENDER_RES` включается экспериментальный
динамический путь, описанный выше. Запуск пересобирает порт и использует
локальные файлы `CUSA03173`; наличие исходников и бинарника само по себе
не подтверждает воспроизводимость на другом ПК.

## Исправление 29 сентября: живая смена пресета

Причин, по которым смена пресета в меню не меняла картинку, было две:

1. `SceneTargets` копировал цели между нативным и уменьшенным размером только
   через `vkCmdBlitImage`, а RADV не даёт blit для `D32S8`. Поэтому глубина
   сцены считалась неподходящей и уменьшенный рендер не включался. Теперь для
   depth/stencil-форматов без blit копирование идёт полноэкранной отрисовкой
   (`host_shaders/depth_resample.frag`): глубина пишется через `gl_FragDepth`,
   трафарет через `VK_EXT_shader_stencil_export`.
2. Маска реактивности (`reactive=1`) снимала цвет в 1920×1080 и пересоздавала
   FSR-контекст 1920→1920, а основной проход сразу пересоздавал его под
   уменьшенный вход. Контекст пересоздавался каждый кадр. Теперь маска
   читает уменьшенную цель сцены.

Проверка в тестовом окружении (`out/dyn-res-test.log`): переключения в меню дают
`FSR 3 context 1280x720 / 1130x636 / 960x540 / 640x360 -> 1920x1080`,
по одному пересозданию на смену пресета, без сбоев. FPS в этой сцене около
54–56 на всех пресетах, то есть узкое место здесь не в разрешении 3D.

## 30 сентября: FSR 4 INT8 и производительность

### FSR 4 (v07 INT8/DOT4)

- `vk_fsr4.cpp/.h`: провайдер FSR-Vulkan `ffxFsr4V07*` с моделью под пресет (native,
  quality, balanced, performance, ultraperf), тир 1080. Входы те же, что у FSR 3.1.
  В меню «Апскейлер → FSR 4 (INT8)», в ini `upscaler=fsr4`, env `BB_UPSCALER=fsr4`.
  Если нет ассетов или возможностей GPU, автоматически включается FSR 3.1.
- Ассеты: `fetch_fsr4_assets.sh` скачивает набор, собранный Q2RTX из MIT-исходников
  FidelityFX SDK (`fsr4_shaders/`, в `.gitignore`, 98 SHA-256 сверены с манифестами).
  `BB_FSR4_DIR` задаёт другой каталог.
- Устройство: включены `shaderIntegerDotProduct` и `VK_KHR_compute_shader_derivatives`
  (`Instance::IsFsr4Int8Supported`).
- Проверено в тестовом окружении: модели quality/ultraperf создаются, при смене пресета
  фриз ~6,5 с (компиляция). Пользователь: картинка чётче FSR 3.1, но сильный гостинг
  на персонаже и оружии. Векторы проверены отладочным видом, они корректны:
  персонаж получает векторы объекта. В SPIR-V pre-прохода глубина выбирается
  по минимуму (как у нас), векторы трактуются как «прошлая − текущая». Для A/B
  в меню: «FSR 4: авто-экспозиция», «FSR 4: обратный знак jitter».

### Производительность (perf, поток GPU-команд)

- `SceneTargets::Eligible` спрашивал у драйвера свойства формата на каждую отрисовку:
  ~13–15% времени потока GPU. Теперь кеш по формату.
- `ObjectMotion::Attach`, снимок цвета и маска реактивности вызывали
  `Scheduler::CommandBuffer()`. Это переводило запись всего остатка сабмита (почти
  весь G-buffer) на поток GPU. Теперь они идут через `Scheduler::Record`.
  Остались два прямых вызова в конце кадра (`TemporalUpscaler::Run`, презентер).
- Итог: поток GPU ~74% вместо ~94% одного ядра. В игровых сценах 61–98 FPS против
  53–87 до исправлений (сцены не совпадают один в один, это ориентир).

### Профиль с DWARF-стеком (perf, поток GPU-команд, 30.09)

- `Motion::IndexedRange` (скан и хеш индексов для векторов объектов) занимал ~10% потока
  GPU. Добавлен `Motion::IndexRangeCache`: результат переиспользуется и полностью
  перепроверяется раз в 32 кадра. В игре ~98% диапазонов из кеша (260 записей).
- `SceneTargets`: плоская таблица свойств форматов и память последних восьми целей;
  вместе с Attachment/Get/View/Eligible ~4% вместо ~7%.
- После этого поток GPU загружен работой без заметных ожиданий. Поток записи Vulkan
  ~40% работы и ~57% ожидания. GPU в среднем ~65% занятости.
  Ограничивает кадр поток GPU-команд. Главные статьи — базовые затраты видеоядра:
  FindView ~5,6%, BindTextures ~5,6%, memmove ~4,6%, SmallGuestCopy ~3,5%,
  CachedImageDescEntry ~3,2%, BindBuffers/BindVertexBuffers ~3% каждая.
  Следующий шаг — перенос этих вычислений на рабочие потоки (шаг 2 parallel_gpu.md).

### FSR 4: гостинг на персонаже и оружии (30.09, повторная проверка)

Видео `video_2026-09-30_03-43-12.mp4`: FSR 4, Ultra Performance (640×360 → 1920×1080). За
движущимся диском пилы остаётся тёмный отпечаток на открывшемся фоне. Проверено:

- отладочный вид векторов (FSR 4): персонаж и оружие получают векторы объекта;
- кеш диапазонов индексов не устаревает (0 изменений при перепроверках);
- последовательность jitter совпадает с провайдером (Halton 2/3, ceil(8·ratio²) фаз);
- A/B в одном запуске с выключенными оптимизациями после 29.09 (биты 4096, 8192, 1<<30):
  шлейфы одинаковые в обеих фазах, то есть это не регрессия от них. Попутно: эти
  оптимизации вместе дают 84,4 против 70,8 FPS при беге (+19%).

Модель v07 определяет открывшийся фон по цвету (глубина используется только для расширения
векторов), и при входе 640×360 ей мало информации. FSR 3.1 отбрасывает такую историю по
глубине, поэтому на Ultra Performance шлейфов у него меньше.
