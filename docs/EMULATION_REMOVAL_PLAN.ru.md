# Уход от эмуляции: что сделано и что дальше (2026-10-06)

## Где проходит граница API

Bloodborne собран со статической libGnm. Пакеты PM4 пишет не драйвер, а сама игра, функциями
`sce::Gnm::*CommandBuffer` (`0x1068000–0x10a0000`, `0x11fd000–0x11fe000`). Перехват всех таких
функций (`BB_GNM_OBSERVE=1`) показал: 100 % отправляемых пакетов пишут известные вызовы API, всего
99 методов. Gnm — API, который пишет регистры: `setDepthStencilControl` = один `SET_CONTEXT_REG`.
Поэтому разбор PM4 от этих 99 функций и трансляция самих вызовов дают одно и то же; PM4 здесь —
формат записи вызовов, как командный список. Он уже разбирается параллельно (DrawPreparation).

Эмуляция железа — не разбор пакетов, а то, что делается вместо GPU:

| Что | Состояние |
|---|---|
| Модель памяти 0.2 (копии в VRAM, защита страниц, обратное чтение, ранние метки) | Запасной вариант. Модель ПК — по умолчанию, для NVIDIA режим «кусок на выделение». Удалить код 0.2 после проверки на NVIDIA. |
| Метки EOP/EOS | Модель ПК: пишутся после завершения работы GPU (честно). |
| `WaitRegMem` на метки той же очереди | Транслируется как выполненное ожидание (порядок очереди); ждать CPU не нужно. |
| `WRITE_DATA`/DMA ждали все копии хоста | Ждут только пересекающиеся копии (как командный процессор, который не ждёт шейдеров). |
| Constant Engine (CE RAM, дампы, счётчики) | Выполняется на CPU в порядке потока: наш разборщик читает описатели из памяти. |
| SRT walker (код шейдера GCN, исполняемый на CPU) | Нужен по той же причине. |
| Учёт записей GPU для разборщика (`PendingWriteOverlaps`, `IsRegionGpuModified`) | ~15 % потока GpuComm, та же причина. |
| Кэш текстур по адресу + хеш | Та же причина плюс отсутствие объектов «текстура» в PM4. |

Почти вся оставшаяся эмуляция существует потому, что **транслятор читает описатели ресурсов
(T#/V#/S#) из памяти игры на CPU во время разбора**. Драйвер ПК и DXVK так не делают: память
приложения читает GPU во время выполнения.

## Дальше, по порядку

1. **NVIDIA.** Тестовая сборка `dist/Bloodborne-bbport-x86_64-test-1006.AppImage` (модель ПК по
   умолчанию, режим «кусок на выделение»). Если работает — удалить модель 0.2 целиком
   (`page_manager`, `fault_manager`, обратное чтение, BB_UFFD, предзагрузка, ранние метки).
2. **Распараллелить стадию B** (запись отрисовок; на 4 ядрах занята на 99 %, ~3,3 мкс на
   отрисовку, равномерно по привязке буферов/текстур, началу прохода, вершинам). Варианты:
   (а) несколько потоков стадии B по диапазонам отрисовок внутри прохода рендеринга (у каждого
   свой сегмент команд; общие кэши уже под блокировками; порядок барьеров — по проходам);
   (б) разрешение привязок (буферы/текстуры → Vulkan) на стадии A, где 28 % простоя, а B только
   записывает. Нужны прогулочные тесты.
3. **Описатели на GPU (главный шаг к «как DXVK»).** Шейдер читает T#/V#/S# сам (буферы на месте
   и BDA уже есть); текстуры — bindless-массив, T# → индекс через таблицу на GPU, которую
   ведёт кэш текстур при создании образов. Тогда не нужны SRT walker, CE на CPU, учёт ожидающих
   записей; `WRITE_DATA`/DMA/дампы CE становятся записями GPU в порядке потока. Большой проект.
4. **Текстуры как объекты.** Перехват `Gnm::Texture::init*` и загрузчика TPF
   (`CSGXTextureCreateFragment`): образ создаётся при загрузке, а не угадывается по адресу;
   хеши и наложения адресов уходят. Ассеты можно заранее перевести в линейный вид (детайлинг
   один раз при установке).
5. **Шейдеры заранее.** Все шейдеры GCN из файлов игры → SPIR-V при установке; без компиляции
   во время игры.

Что остаётся трансляцией, как у DXVK: шейдеры GCN → SPIR-V, описатели и форматы → Vulkan.

## Шаг 1 (2026-10-07): движок констант больше не синхронизируется с записью отрисовок

Замеры (`BB_CE_STATS=1`, Яр'гул): ~14 000 `DumpConstRam` в секунду, ~4–5 МБ/с, всего 25 страниц
(кольцо ~100 КБ). Каждый дамп читается ровно одним указателем из user data — это таблицы
описателей для SRT walker. Константы, вершины, индексы, большие буферы из этих страниц не
читаются; шейдеров, читающих память самостоятельно (`uses_dma`), нет. То есть дампы CE нужны
только транслятору — это построение таблиц описателей, а не данные для GPU.

Ожидания стадии A на дампах (`WaitForPendingReads`) были нужны только потому, что стадия B для
отрисовок без подготовки сама перечитывала таблицы V# (описатели вершинных буферов) — к тому
времени перезаписанные следующим дампом (~15 % V# оказывались чужими: баг DoF, issue #44).

Сделано:
- стадия A снимает V# в пакет отрисовки, стадия B берёт их оттуда и таблицы не читает;
- источник DMA отмечается точным диапазоном, а не «читает неизвестно что».

Итог: ожиданий на дампах ~850/с → ~46/с, стадия A ждёт 1,5 % времени вместо ~30 %
(16 потоков). На 4 ядрах / 8 потоках FPS тот же (~170): там узкое место — стадия B
(3,4 мкс на пакет; больше всего — `ObtainBuffer` 0,57 мкс: сопоставление адресов памяти игры с
буферами GPU).

Записи командного процессора (`BB_CE_STATS`): `WRITE_DATA` ~8 400/с в 2 страницы (читаются как
константы ~240/с), DMA ~1 000/с в 15 страниц. Они пишут данные для GPU, и их перевод — команды
GPU в порядке потока (`vkCmdUpdateBuffer`, у DMA для памяти на месте уже так). Для `WRITE_DATA`
это упирается в правило переноса часто записываемых GPU блоков в VRAM — делать вместе с
упрощением модели памяти.

## Шаг 2 (2026-10-07): синхронизации стадии B

Стадия B (запись отрисовок) — узкое место на 4 ядрах (занята 99 %). Задачи кадра на ней:
- сигнал flip = подготовка кадра презентером; 600 тыс. тактов на кадр, из них работы ~40 тыс.,
  остальное — ожидание потоков записи команд (`CommandBuffer()`) и синхронная отправка. Теперь
  ~50 тыс.: презентер записывается через `Record`, отправка асинхронная;
- проходы апскейлера пишут команды напрямую — для них отдельный сегмент без ожидания;
- DMA (~900/с, 4 байта) ждали копии и сигналы даже когда запись делает GPU — ждут только для
  записей CPU.

Что осталось на стадии B (мкс на пакет, 3,5 всего): привязка ресурсов 1,0 (буферы 0,4, текстуры
0,45), `ObtainBuffer` 0,6, начало прохода 0,26, вершины 0,34, задачи 0,2. Дальше —
разделение стадии B или привязка ресурсов на стадии A (см. п. 2 выше).
